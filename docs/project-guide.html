AURUM

From S&P 500 prices and filings to paper-traded decisions.

AURUM ingests market and SEC data into Postgres, builds a feature table with dbt, trains a LightGBM ranking model, and turns the scores into BUY, SELL and HOLD. Orders go only to an Alpaca paper account.

How the components connect

Each stage writes something the next one reads. Postgres gold is the single hand-off point: modeling and the MCP server both read only from it.

Run it

Python 3.12, managed with uv. Secrets are environment variable names in the configs and live in .env.

Install

uv sync --locked --no-build
uv run ruff check src/ main.py
uv run pytest tests/ -v

Ingest one feed

# -f False resumes from watermarks. Default is a full load.
uv run python -m src.ingestion.cli -c src/ingestion/configs/yahoo/ohlcv_1d.yaml -f False

Build the warehouse

cd src/transformation/aurum_dwh
uv run --group dbt dbt deps
uv run --group dbt dbt seed
uv run --group dbt dbt build

Train, then decide

uv sync --group modeling
uv run python -m src.modeling.cli train -c src/modeling/configs/lgbm_xs_excess_5d.yaml
uv run --group modeling python -m src.inference.cli decide

Paper trade (orders shown, none sent)

uv run --group modeling --group paper python -m src.paper.cli rebalance --dry-run

Everything in one image

docker compose -f docker-compose.modeling.yml build trainer
docker compose -f docker-compose.modeling.yml run --rm trainer infer decide
# first arg after trainer: ingest | dbt | model | infer

Ingestion

One YAML config fully specifies a run. Data goes straight into Postgres; no Kafka is in the code path.

  1. Load and build. runner.run_feed() reads the config and the factory returns a feed. Classes are found by registry name, so every new feed or datasource module must be imported in runner.py.
  2. Staleness gate. A config with min_refresh_gap_days (the six EDGAR configs set 10) is skipped when its landing table is fresher than that. The run returns SKIPPED_FRESH and exits 0.
  3. Watermarks. With -f False, MAX(date) GROUP BY symbol on the landing table, and each symbol resumes the next day.
  4. Read in chunks. Yahoo yields one frame per batch_size symbols, so peak memory is one batch.
  5. Process. Feed.process() is the only per-feed code. It uppercases columns and runs once per chunk, so it must stay row-wise.
  6. Stamp and write. Adds RUN_DATE, EXECUTION_ID and an md5 primary key, then appends to the sink in 50k-row chunks.
SourceModeNotes
Yahoo OHLCVIncremental by watermark100 symbols per batch
EDGAR statementsFull load, six configs10 requests per second cap. truncate.py empties each table first because the sink does not deduplicate.
Exit codes matter

The CLI exits 1 on FAILED. Step Functions relies on that to mark the run failed, so do not remove it.

Warehouse

A dbt project on Postgres, not Snowflake. Three layers, all tested (2 warnings on documented real-data outliers, 0 errors).

LayerModelsPurpose
bronze8 br_*Mirrors the landing tables
silver3 stg_*, 5 int_*Cleaned statements and engineered features
gold4 mart_*ML-ready marts. mart_features is the model input.
  • Prices before fundamentals. Silver joins the two, so building over fresh statements and stale prices would be as-of two different dates.
  • Point-in-time lag. Fundamentals are lagged so a model never sees a filing before it was public.
  • Schema names. generate_schema_name is overridden so bronze, silver and gold are used as written.
  • Seeds. company_meta, concept_map, selected_features.

Modeling

The task is cross-sectional ranking: which stocks beat the market over five days. The target is fwd_ret_5d_excess, not the raw return, because SHAP on the raw target collapses onto market-regime columns.

CommandDoes
trainFits LightGBM across purged walk-forward folds and writes a versioned run
evaluateHoldout rank IC, ICIR and decile spread into metrics.json
select-featuresSHAP ranking written to selected_features.csv
backtestCost sweep to a break-even bps, factor attribution, signal-lag and deflated-Sharpe checks; writes backtest/report.html
comparePromotion gate: narrowed vs full model on holdout ICIR and decile spread
predictScores a given as-of date
  • Purge and embargo. The naive fold_id <= k split leaks across the target horizon.
  • Holdout. Folds 298 to 321, about 2024-10 to 2026-09, never used for training.
  • Replayable preprocessing. Every step must replay against mart_features alone. NaNs are kept for LightGBM.
  • Registry. Flat files under models/, addressed by version or latest.

Inference

decide scores the newest trained run on the latest gold date. Top decile is BUY, bottom decile SELL, the rest HOLD. A stale-date guard refuses to decide on old data. replay backtests the same rule against a momentum baseline.

Caveat

Holdout IC is 0.007 and break-even cost is 18 bps. The signal is weak, and every output carries that warning.

Hosted on a t3.micro EC2 with a read-only Postgres role, reachable only through an SSM port-forward.

Paper trading

The only order placement in the project, and only against an Alpaca paper account. It needs the paper dependency group, plus backtesting for the engines. It is not scheduled on AWS.

AlpacaBroker talks to Alpaca and SimBroker simulates fills. Lumibot runs in a child process with mcp<2 because src/mcp needs mcp 2.x.

AWS schedule

RDS Postgres, one ECR image run as four ECS Fargate task definitions, and three Step Functions state machines started by EventBridge Scheduler. Terraform is in infra/terraform/.

State machineCron (UTC)States
aurum-daily-market30 22 ? * MON-FRI *ingest-market, dbt
aurum-semimonthly-edgar0 6 1,15 * ? *ingest-market, ingest-edgar, dbt
aurum-monthly-train0 12 1 * ? *train

Why it is shaped this way

  • dbt after every ingest. gold.mart_features is only as fresh as the last build. The EDGAR cron can fire on a weekend while the daily machine is weekdays only, so EDGAR carries its own dbt state.
  • Prices before fundamentals. EDGAR's machine ingests market data first, because silver joins the two.
  • dbt and train are separate states. A dbt failure must never reach training.
  • Failure is loud. Every ECS state is ecs:runTask.sync, which fails on a non-zero exit. Failures publish to SNS and end the execution red.
  • One command per task. Each task definition's command holds the whole workflow as sh -c "a && b && c", so the machines have one or two states each.

CI and deploy

CI runs on main, develop, epic/* and pull requests: ruff, pytest with coverage, then SonarCloud. Dependencies install with uv sync --locked --no-build across the modeling, mcp, paper and backtesting groups.

  1. A merge to main triggers terraform.yml.
  2. The apply job waits for a reviewer on the apply environment.
  3. It assumes the aurum-github-actions role through OIDC.
  4. scripts/deploy.sh apply builds the app image (<sha>) and the MCP image (mcp-<sha>), pushing a tag only if ECR does not already hold it.
  5. Terraform applies. A merge that changes src/ ships to Fargate with no local step.

image_tag is the short SHA of the last commit touching an image path, not HEAD, so an infra-only commit rebuilds nothing. For rollback, run make push locally with -var="image_tag=<older sha>".

Gotchas

  • A fresh database means a full load whatever -f says. The ingest task is sized for daily increments, so a backfill needs run-task --overrides with more memory.
  • The sink does not deduplicate. Append-only writes are safe for watermarked feeds. EDGAR feeds must be truncated first, one config at a time.
  • Memory. An unchunked first load of 503 symbols from 2000 OOM-killed the 8 GB ingest task (exit 137) on 2026-09-06. batch_size is the knob.
  • Uppercase columns. Feeds, configs, primary keys and watermarks all use uppercase names, and Postgres identifiers are quoted.
  • Missing group, CI-only failure. A ModuleNotFoundError that appears only in CI means a dependency group is missing from the install step.
